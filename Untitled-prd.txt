
# PRD — InvoiceMatch AI OS

## 1. Project Overview

Build a small AI-assisted operations system called **InvoiceMatch AI OS**.

The system helps a finance, accounts-payable, or operations employee compare a vendor invoice against its corresponding purchase order (PO).

The core workflow is:

Upload Purchase Order + Upload Invoice
        ↓
Extract structured information from both documents
        ↓
Validate extracted data
        ↓
Compare PO and Invoice using deterministic rules
        ↓
MATCH / EXCEPTION / INVALID
        ↓
Show evidence and reasons
        ↓
Human reviews exceptions
        ↓
Save the decision
        ↓
Export/store the result in Google Sheets

The system must be simple enough that a non-developer can operate it without developer assistance.

The product should be presented as an **AI-assisted document matching workflow**, not as a production accounting or payment system.

---

# 2. Problem

Finance and operations teams often manually compare invoices with purchase orders.

A typical manual process requires an employee to:

1. Open the purchase order.
2. Open the invoice.
3. Check vendor name.
4. Check PO number.
5. Check currency.
6. Compare line items.
7. Compare quantities.
8. Compare unit prices.
9. Compare taxes and subtotals.
10. Compare the final total.
11. Decide whether the documents match.
12. Investigate discrepancies.

This is repetitive, time-consuming, and prone to human error.

The system should reduce repetitive document comparison while keeping humans responsible for uncertain or financially sensitive decisions.

---

# 3. Target User

Primary user:

- Finance/AP employee
- Operations employee
- Small-business back-office employee

The user should not need programming knowledge.

The intended experience should be:

> Upload PO → Upload Invoice → Click Compare → Understand Result → Review Exception → Approve/Reject → Done

# 4. Product Goal

Build a reliable prototype that demonstrates how AI can automate the repetitive parts of invoice-to-PO matching while keeping deterministic business rules and human review in control.

The system must demonstrate:

- AI document understanding
- Structured data extraction
- Deterministic comparison
- Exception detection
- Human-in-the-loop review
- External API integrations
- Persistent storage
- Evaluation and testing
- Clear evidence for every decision
- Non-developer usability

---

# 5. Core Design Principle

Use AI where AI is useful.

Use deterministic code where deterministic logic is required.

Use humans where judgment is required.

### AI / Groq

Use Groq to extract structured information from unstructured PDF documents.

### Python

Use Python deterministic logic for:

- Numeric comparisons
- Field comparisons
- Line-item comparisons
- Tolerance checks
- Match/exception decisions
- Validation
- Business rules

### Human

A human must review uncertain or exceptional cases.

The LLM must NOT independently make the final financial matching decision.

The final result should be generated by the deterministic matching engine.

---

# 6. MVP Scope

The MVP should support:

1. Upload one Purchase Order PDF.
2. Upload one Invoice PDF.
3. Extract text from PDFs.
4. Send extracted document content to Groq.
5. Receive structured JSON.
6. Validate the JSON using Pydantic.
7. Normalize comparable fields.
8. Compare the documents.
9. Generate a detailed comparison result.
10. Classify the result as:
   - MATCH
   - EXCEPTION
   - INVALID DOCUMENT
11. Display the result in the web UI.
12. Show exactly why an exception occurred.
13. Allow a human to approve/reject an exception.
14. Save processing and review history in SQLite.
15. Export completed comparison results to Google Sheets.
16. Provide an evaluation interface for the predefined test cases.
17. Provide tests for the core system.

Do not expand the MVP into a complete accounting platform.

# 9. Document Data Contracts

Use strict Pydantic models.

## Purchase Order Schema

```json
{
  "document_type": "purchase_order",
  "po_number": "PO-1001",
  "vendor_name": "Acme Supplies",
  "currency": "USD",
  "items": [
    {
      "description": "Laptop",
      "quantity": 2,
      "unit_price": 1000.00,
      "total_price": 2000.00
    }
  ],
  "subtotal": 2000.00,
  "tax": 360.00,
  "total": 2360.00
}
```

## Invoice Schema

```json
{
  "document_type": "invoice",
  "invoice_number": "INV-1001",
  "po_number": "PO-1001",
  "vendor_name": "Acme Supplies",
  "currency": "USD",
  "items": [
    {
      "description": "Laptop",
      "quantity": 2,
      "unit_price": 1000.00,
      "total_price": 2000.00
    }
  ],
  "subtotal": 2000.00,
  "tax": 360.00,
  "total": 2360.00
}
```

All monetary values should use a safe numeric representation appropriate for financial calculations.

Do not use floating-point arithmetic carelessly for financial comparisons.

Prefer Python Decimal where appropriate.

# 10. Extraction Rules

The Groq extraction service must:

1. Receive extracted document text.
2. Determine the document type.
3. Extract the required fields.
4. Return structured JSON.
5. Follow the predefined schema.
6. Never invent values.
7. Use null when information is genuinely unavailable.
8. Avoid adding unnecessary fields.
9. Return valid JSON only.

If the document does not contain a value, return:

```json
null
```

Do not guess.

Example:

If the invoice does not contain a PO number:

```json
{
  "po_number": null
}
```

Do not generate a PO number based on context.

# 13. Normalization

Create:

```text
app/services/normalizer.py
```

Normalization should be conservative.

For text:

* lowercase
* trim whitespace
* collapse repeated whitespace
* normalize basic punctuation where safe

For example:

```text
"  Acme  Supplies "
```

becomes:

```text
"acme supplies"
```

Do not implement aggressive semantic matching in the MVP.

For item descriptions, basic normalized comparison is sufficient.

If item matching is uncertain, classify the case as an exception rather than guessing.

# 16. Match Result

The matching engine should produce a structured result similar to:

```json
{
  "status": "MATCH",
  "confidence": "HIGH",
  "reasons": [],
  "field_comparisons": [],
  "exception_count": 0
}
```

For an exception:

```json
{
  "status": "EXCEPTION",
  "confidence": "LOW",
  "reasons": [
    "Invoice quantity is 5 but PO quantity is 4"
  ],
  "field_comparisons": [],
  "exception_count": 1
}
```

The system should explain the decision using the actual comparison evidence.

---

# 17. Result Categories

Only use these primary result categories:

## MATCH

All required comparisons pass the configured rules.

## EXCEPTION

The documents are readable and structurally valid, but one or more comparisons fail or are uncertain.

Examples:

* Quantity mismatch
* Price mismatch
* Vendor mismatch
* PO number mismatch
* Total mismatch
* Uncertain line-item mapping

## INVALID DOCUMENT

The document cannot be reliably processed.

Examples:

* Corrupted PDF
* Empty PDF
* Unsupported scanned document
* Invalid extraction
* Missing critical structure

# 29. Retry and Fallback Behavior

Retries should only be used for appropriate transient failures.

For example:

* Groq temporary network failure → limited retry
* Groq rate limit → graceful error / retry later
* Google Sheets temporary failure → allow later export

Do not endlessly retry.

If extraction cannot be trusted, stop processing and mark the document as invalid or requiring review.

---

# 30. Confidence

Confidence should NOT be treated as the final financial decision.

Use confidence primarily to communicate extraction or comparison reliability.

For example:

```text
HIGH
MEDIUM
LOW
```

A low-confidence or uncertain comparison should become an EXCEPTION.

Never use:

> "The AI is 95% confident, therefore approve the invoice."

The deterministic comparison rules and human review must remain authoritative.

# 43. Non-Developer UX Requirements

The application must be understandable without reading the source code.

A new user should be able to understand the main workflow within approximately 30 seconds.

The main action should be obvious:

```text
Upload PO
+
Upload Invoice
↓
Compare Documents
```

Results must use clear language.

Avoid technical messages such as:

```text
Pydantic validation exception at line 124
```

Instead show:

```text
We couldn't reliably read the invoice.
Please check that the PDF contains readable text and try again.
```

Technical details should remain in backend logs.

# 45. Performance

The system does not need production-scale optimization.

However:

* Avoid unnecessary Groq calls.
* Extract each document once per comparison.
* Do not call the LLM for deterministic comparison.
* Keep processing asynchronous where appropriate.
* Show processing status to the user.
* Measure end-to-end processing time.

# 47. Important Product Safety Rule

Because this workflow touches financial documents:

The system must never claim that an invoice is safe to pay solely because an LLM said so.

The architecture must enforce:

```text
LLM extraction
       ↓
Validated structured data
       ↓
Deterministic comparison
       ↓
Human review for exceptions
```

The LLM is responsible for understanding unstructured documents.

The deterministic engine is responsible for comparison.

The human is responsible for resolving exceptions.
